## 1 选题背景及意义

在高校校园中，学生遗失物品的情况频繁发生。传统的失物招领方式主要依赖公告栏张贴、QQ群/微信群发布消息等，存在信息分散、查找效率低、缺乏位置标注、认领流程不规范等问题。同时，校园内不同校区之间的物品流转也增加了失物找回的难度。

针对以上痛点，本课题设计并实现了一套**校园失物招领与位置追踪系统**。系统基于 B/S 架构，以地图可视化服务为核心，结合失物发布、拾物招领、预约领取、后台审核、管理员分级管理等功能模块，旨在为高校师生提供便捷、高效、透明的失物招领服务。

**选题意义：**

1. 提高失物找回效率：通过地图标记物品的遗失/拾取位置，直观展示物品空间分布，降低信息检索成本。
2. 规范认领流程：引入预约—审核—确认的闭环机制，防止冒领误领，保障失主权益。
3. 推动校园服务数字化：将传统的人工招领模式迁移至线上平台，符合智慧校园建设趋势。
4. 锻炼工程实践能力：项目涵盖前端、后端、数据库、地图 API 集成、云存储等技术栈，是综合性的工程实践训练。

## 2 项目功能分析

### 2.2 项目设计目标

1. **功能完整性**：覆盖失物招领全流程，从发布、查找、认领到归还，形成业务闭环。
2. **用户体验优先**：以地图为交互核心，支持多校区切换、标记渲染、位置搜索等直观操作。
3. **安全与规范**：密码使用 werkzeug 哈希加密存储、管理员分级权限控制、审核流程防冒领。
4. **数据规范化**：数据库遵循第三范式设计，消除冗余字段，使用关联表表达多对多关系。
5. **代码可维护性**：前后端分离架构（Vue 3 + Flask），Flask Blueprint 模块化路由，统一 RESTful API 设计。

### 2.3 功能结构分析（功能结构图）

开发本系统目标在于：应用信息化管理手段，结合高校失物招领的实际业务流程，构建一套基于 B/S 架构、以地图可视化服务为核心的失物招领与位置追踪系统。系统将传统的人工招领模式迁移至线上平台，实现失物发布、拾物招领、预约领取、后台审核、消息通知等功能的一体化管理，从而大幅提高失物找回效率，规范认领流程，降低校园后勤管理成本。

校园失物招领与位置追踪系统的总体任务是：使校园失物招领管理更加规范化、自动化和高效率，所以本系统需要完成的功能如下：

（1）在用户认证模块中，实现对普通用户和管理员的身份管理，支持邮箱/用户名注册与登录，密码使用 werkzeug 哈希加密存储。同时提供实名认证功能，用户提交身份证明材料后由管理员审核，确保平台用户身份的真实性。

（2）物品业务模块主要由失物发布、拾物发布、物品浏览与搜索、申请认领、归还确认及预约领取六部分组成。用户可在地图上标记物品位置并上传图片（存储于腾讯云 COS），其他用户可按分类、类型、关键词筛选浏览，提交认领申请并在线预约领取时间。该模块是系统的核心业务入口，覆盖了物品从发布到最终归还的完整生命周期。

（3）地图服务模块以高德地图 JSAPI 2.0 为基础，提供多校区切换、物品标记渲染、3D 视角、搜索定位等功能。通过 `@amap/amap-jsapi-loader` 动态加载地图 SDK，结合 Vue 3 响应式数据绑定实现标记的实时更新。导航子模块基于 Dijkstra 最短路径算法实现校园室内导航，帮助用户快速找到物品所在建筑的具体位置。

（6）消息通知模块支持系统通知和站内消息的发送、列表展示和已读标记。当审核结果更新、关注关系建立或物品状态变更时，系统自动生成通知记录，确保用户及时获取关键信息。

**2、所用技术及分析**

（1）**前端框架：Vue 3 + Vite**

Vue 3 是目前主流的前端渐进式框架，采用组合式 API（Composition API）和响应式数据绑定机制，组件化开发效率高，代码可维护性强。Vite 是 Vue 团队推出的新一代前端构建工具，基于原生 ES Module 实现冷启动和 HMR 热更新，开发体验远优于传统的 Webpack。两者配合使用，能够快速搭建现代化单页面应用（SPA），适合本项目多页面、多组件的前端架构需求。

（2）**后端框架：Flask**

Flask 是 Python 生态中最流行的轻量级 Web 框架之一。其核心精简但扩展性强，通过 Blueprint 机制支持模块化路由组织（本项目共注册 12 个 Blueprint），非常适合中小型项目的快速开发。Flask 内置了 `werkzeug.security` 密码哈希工具，无需额外安装加密库。配合 Flask-CORS 可方便地处理前后端分离架构下的跨域请求。Python 语言本身语法简洁、生态丰富，便于与数据库、云存储等服务集成。

（3）**数据库与 ORM：MySQL + SQLAlchemy**

数据库选用 MySQL 8.0（部署于腾讯云 CynosDB），支持事务、外键约束和 utf8mb4 字符集，InnoDB 引擎保障数据一致性与高并发读写性能。云数据库具有高可用、自动备份的优势，省去了本地数据库的运维成本。ORM 框架采用 SQLAlchemy 2.x（集成 Flask-SQLAlchemy），支持声明式模型定义和原生 SQL 混合使用——核心查询使用 ORM 提高可读性，复杂联表查询使用 PyMySQL 原生 SQL 保证灵活性。数据库连接配置统一由 `common/db_config.py` 管理，通过 `.env` 环境变量切换开发/生产环境。

（4）**地图服务：高德地图 JSAPI 2.0**

高德地图是国内成熟稳定的地图服务商，JSAPI 2.0 提供了标记渲染、地点搜索、地理编码、3D 视角、路径规划等丰富接口，完全满足校园失物招领场景下的地图可视化需求。通过官方 `@amap/amap-jsapi-loader` npm 包解决 AMD 模块与 Vite ES Module 机制的兼容问题。系统支持多校区地图配置切换，结合 Vue 3 响应式数据实现标记的实时增删与状态更新。

（5）**云存储：腾讯云 COS**

物品图片和用户头像存储于腾讯云 COS 对象存储服务。COS 具有高可用、低成本、无限扩容的特点，避免了本地存储的磁盘空间限制和多实例文件共享问题。封装 `utils/cos_utils.py` 单例客户端，通过临时签名 URL（预签名 URL，有效期 3600 秒）安全访问私有存储桶中的图片资源，兼顾安全性和访问性能。

（6）**导航算法：Dijkstra 最短路径**

校园室内导航功能基于经典 Dijkstra 最短路径算法实现（`nav/dijkstra.py`）。将校园建筑内部的关键节点（楼梯口、走廊交叉点、房间门口等）抽象为图的顶点，路段抽象为带权边，通过邻接表存储图结构，计算从当前位置到目标建筑的最短路径，辅助用户快速定位物品所在位置。

（7）**选择分析总结**

本项目的技术选型以"高效开发、易于维护、适配校园场景"为核心原则。前端选用 Vue 3 + Vite 组合，兼顾开发效率与运行性能；后端选用 Flask，保持架构轻量且足够灵活；数据库使用云 MySQL，降低运维负担；地图与云存储采用国内成熟的商业服务（高德、腾讯云），保障服务的稳定性和可用性。整体技术栈均为当前业界主流方案，学习成本适中，社区支持完善，适合作为工程实践项目的技术选型。

### 2.5 技术难点及其解决方案

**难点一：高德地图 JSAPI 在 Vue 3 + Vite 环境下的集成**

高德地图 JSAPI 2.0 以 AMD 模块方式发布，而 Vite 基于 ES Module 机制。若直接在 Vue 组件中 `import` 会导致 `Failed to resolve import "@amap/amap-jsapi-loader"` 错误。解决方案：先执行 `npm install @amap/amap-jsapi-loader --save` 安装官方加载器，在 `src/utils/amapLoader.js` 中封装异步加载函数，Vue 组件 `onMounted` 阶段通过 Promise 调用加载器初始化地图实例。同时处理了多校区切换时的标记清除与重绘逻辑，防止内存泄漏。

**难点二：多表关联下的数据冗余治理**

初始数据库设计中，`lost_item` 表直接存储 `campus_id`，`user_verify` 表存在与 `user` 重复的 `phone`/`email` 字段，`claim` 与 `claim_form` 表功能重叠。各业务表中各自维护审核状态字段，审核逻辑分散。解决方案：编写 Python 数据库迁移脚本（位于 `backend/init/optimize_*.py`），将直接外键替换为关联表（`item_campus`、`repair_campus`），删除冗余字段，合并功能重复的表，创建统一 `audit` 表通过 `target_type` 和 `target_id` 关联不同业务表。

**难点三：审核中心的多类型审核统一处理**

系统中存在认领审核、归还审核等多种审核类型。为避免为每种审核创建独立表导致表膨胀，设计了统一的 `audit` 表，通过 `target_type` 字段（'claim'/'return' 等）区分审核类型，`target_id` 关联对应业务记录。后端实现于 `admin/admin_audit_api.py`，支持按类型和状态筛选、分页查询，使用 `admin_required` 装饰器统一鉴权。

### 3.1 物品发布模块

**功能分析：**

物品发布是系统的核心入口。用户在地图上选择位置，填写标题、描述、分类，上传图片后提交。后端接收表单数据后写入数据库。实际发布接口位于 `backend/map/lost_item/lost_item_publish.py`，路由为 `/api/map/publish`。

**数据库设计：**

物品数据存储于 `lost_item` 表（模型定义于 `models.py`）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `item_id` | INT (PK, autoincrement) | 物品唯一标识 |
| `title` | VARCHAR(100) NOT NULL | 物品标题 |

### 3.2 登录注册模块

**功能分析：**

用户通过邮箱或用户名进行注册和登录，管理员通过 `/api/auth/admin/login` 独立入口进入后台。密码加密使用 Flask 内置的 `werkzeug.security.generate_password_hash`，登录状态通过 `flask.session` 维护。实际代码位于 `backend/user/auth.py`。

**数据库设计：**

| 表 | 关键字段 | 说明 |
|----|---------|------|
| `user` | user_id (PK), username (UNIQUE), email (UNIQUE), password_hash, phone, avatar_url, role | 普通用户（模型：user/models.py User 类） |
| `admin` | admin_id (PK, autoincrement), username (UNIQUE), password_hash | 管理员（模型：user/models.py Admin 类） |

**具体实现：**

- 注册流程（`auth.py` 第 8-51 行）：接收 JSON `{username, email, password}` → 检查 username/email 唯一性（SQLAlchemy ORM 查询） → `generate_password_hash(password)` 生成哈希 → `db.session.add(new_user)` → `db.session.commit()` → 异步记录注册日志至 `system_logs`。
- 登录流程（`auth.py` 第 53-104 行）：支持 email 或 username 登录 → ORM 查询用户 → `check_password_hash(user.password_hash, password)` 验证 → 成功则 `session['user'] = user.user_id` 并异步记录登录日志。
- 管理员登录（`auth.py` 第 107-142 行）：查询 `Admin` 表 → 验证密码 → `session['admin_id'] = admin.admin_id`。
- 代码示例：

```python
from werkzeug.security import generate_password_hash, check_password_hash

@auth_bp.route('/register', methods=['POST'])
def register():
    data = request.get_json()
    username = data.get('username')
    email = data.get('email')
    password = data.get('password')

    if User.query.filter_by(username=username).first():
        return jsonify({'message': 'Username already exists'}), 400

    hashed_password = generate_password_hash(password)
    new_user = User(username=username, email=email, password_hash=hashed_password)

    db.session.add(new_user)
    db.session.commit()
    return jsonify({'message': 'User created successfully'}), 201
```

### 3.7 社区用户关注模块

**功能分析：**

在社区模块中，本人负责用户关注功能的开发，实现于 `backend/community/follows.py`（186 行）。提供关注/取关、检查关注状态、粉丝列表、关注列表、关注数量统计等 5 个 API。

**数据库设计：**

`user_follow` 关联表：`follower_id` + `followee_id` 复合主键，唯一约束防止重复关注。

**具体实现：**

- 关注/取关（`/follow`，第 8-63 行）：接收 `follower_id` 和 `followee_id` → 检查 `follower_id != followee_id`（防止自关注） → 查询是否已存在关注关系 → 存在则 DELETE（取关），不存在则 INSERT（关注） → 关注时自动创建通知（INSERT INTO notifications，类型为 'follow'）。
- 粉丝列表（`/followers/<user_id>`，第 91-123 行）：JOIN user 表查询粉丝信息，若传入 `current_user_id` 则批量检查关注状态。
- 关注列表（`/following/<user_id>`，第 125-157 行）：同理，查询当前用户关注的人。
- 关注数量（`/counts/<user_id>`，第 159-185 行）：COUNT 查询 following_count 和 follower_count。

```python
@follows_bp.route('/follow', methods=['POST'])
def follow_user():
    follower_id = data.get('follower_id')
    followee_id = data.get('followee_id')
    if follower_id == followee_id:
        return jsonify({'success': False, 'message': '不能关注自己'}), 400

    cursor.execute("SELECT id FROM user_follow WHERE follower_id=%s AND followee_id=%s",
                   (follower_id, followee_id))
    if cursor.fetchone():
        cursor.execute("DELETE FROM user_follow WHERE ...")   # 取关
        action = 'unfollowed'
    else:
        cursor.execute("INSERT INTO user_follow (...) VALUES (...)", ...)  # 关注
        action = 'followed'
    return jsonify({'success': True, 'action': action})
```

## 5 项目过程中遇到的问题和解决办法

### 5.1 问题1：高德地图 JSAPI 在 Vite 环境下的加载失败

**问题描述：**
在 Vue 3 + Vite 项目 `lost-found` 中，通过 `import` 引入高德地图 JSAPI 时控制台报错 `[plugin:vite:import-analysis] Failed to resolve import "@amap/amap-jsapi-loader" from "src/utils/amapLoader.js"`。

**原因分析：**
`@amap/amap-jsapi-loader` 是高德官方提供的 npm 包，用于在现代打包工具中动态加载高德地图 AMD 模块。项目 `package.json` 中未声明该依赖，Vite 无法解析此 import。

**解决方案：**
1. 执行 `npm install @amap/amap-jsapi-loader --save` 安装依赖包。
2. 在 `src/utils/amapLoader.js` 中封装 `loadAMap()` 函数，通过 Promise 控制 SDK 加载时序。
3. Vue 组件 `onMounted` 阶段调用 `loadAMap()`，确保地图实例初始化完成后再渲染标记。

### 5.2 问题2：数据库冗余字段与表结构不规范

**问题描述：**
项目初期数据库设计存在以下不规范问题：
1. `lost_item` 表直接存储 `campus_id`，无法表达一个物品跨多校区的情况。
2. `user_verify` 表中 `phone` 和 `email` 与 `user` 表字段重复。
3. `claim` 与 `claim_form` 表功能高度重叠。
4. 各业务表中各自存储审核相关字段，审核逻辑分散，查询效率低。

**解决方案：**
编写 Python 迁移脚本逐一优化（位于 `init/` 目录）：
- `optimize_campus_fields.py`：移除 `lost_item` 和 `repair` 中直接存储的 `campus_id`，创建 `item_campus` 和 `repair_campus` 关联表表达多对多关系。
- `optimize_user_verify_fields.py`：删除 `user_verify` 中冗余的 `phone` 和 `email` 字段。
- `optimize_claim_merge.py`：合并 `claim` 表到 `claim_form`，统一认领数据管理。
- `optimize_audit_fields.py`：移除各业务表中分散的审核字段，数据统一迁移至 `audit` 表集中管理。

**经验教训：**
数据库设计应在需求分析阶段充分考虑规范化，避免后期迁移带来的业务代码连锁修改。多对多关系从一开始就应使用关联表而非直接存储外键。

### 5.3 问题3：图片上传与云存储管理

**问题描述：**
物品发布时需上传多张图片。本地 `uploads/` 目录存储存在磁盘空间受限、扩展性差等问题。服务器部署后多实例间无法共享文件。

**解决方案：**
将图片存储迁移至腾讯云 COS 对象存储：
- 封装 `utils/cos_utils.py` 单例客户端，通过环境变量读取 `COS_SECRET_ID`、`COS_SECRET_KEY`、`COS_REGION`、`COS_BUCKET`。
- 上传时生成唯一文件名 `lost_items/{uuid4().hex}{ext}`，调用 `cos_client.upload_bytes()` 上传。
- COS key 数组存入 `lost_item.image_urls` 字段（JSON 类型）。
- 前端通过 `cos_client.get_presigned_url(key, expires=3600)` 获取临时签名 URL 访问图片。
- 对上传文件进行类型校验（仅允许 jpg/png/gif），防止非图片文件上传。
